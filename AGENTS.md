# AGENTS

This file is the **root instruction** for humans and LLMs working in this Dava.Flow Context Warehouse. It gives universal rules and orientation; **detailed process, TDD, review, and completion behaviour live in the Flow Skills installed under `skills/`**.

## Getting Started (Agents)

The human kicks off a session by saying `Let's Flow` (or `/flow` / `$flow` in IDEs that register the command). When that happens:

1. Respond per the `flow.agent` skill: check `.flow/config.toml` for `pending_setup`, then route to the selected phase agent (`signal.agent`, `explore.agent`, or `govern.agent`).
2. Load any skill referenced by the task by reading `skills/<slug>/SKILL.md` **before** acting. Use `dft skills list` to see what is installed; if a required skill is missing, ask the human before installing it with `dft skills add <slug>`.
3. Make the smallest reversible change. Follow TDD for code edits.
4. When closing out, report: files changed, commands/tests run, checks skipped (with reasons), and links to affected code/docs/specs/tasks.

### Skill Loading

- Load a skill by reading `skills/<slug>/SKILL.md` before executing any step it governs.
- Only load skills whose description matches the task at hand; do not speculatively load unrelated skills.
- Treat skill content as **authoritative** over this file for the domain it covers.
- If a task references a skill that is not installed, stop and ask the human — do not invent skill content.

## Step Execution

When executing any skill's step files, follow this rule at all times:

**ONE STEP AT A TIME.** Read step → Execute step → Complete step → Next step.

Forbidden:

- Reading ahead into later step files.
- Batching or merging multiple steps into a single action.
- Skipping step files.
- Auto-advancing past a step that requires human confirmation.

This applies to every skill's `steps/` directory. Skills may add further constraints (e.g. mandatory pauses, validation gates) but must never relax this rule.

## Warehouse Structure

This warehouse follows the Dava.Flow phase-aligned structure:

```
.flow/                          # Turbine configuration
skills/                         # Installed Flow Skills
signal/                         # Signal phase — problem qualification
  signals/                      # Signal definitions
explore/                        # Explore phase — discovery and specification
  epics/                        # Epic definitions
govern/                         # Govern phase — planning and implementation
  releases/                     # Release documentation
evolve/                         # Evolve phase — production optimization
work/                           # Active task workflow
  01-pending-planning/          # Tasks awaiting planning
  02-planning/                  # Tasks being planned
  03-pending-implementation/    # Tasks awaiting implementation
  04-implementing/              # Tasks being implemented
  05-pending-completion/        # Implemented tasks pending final completion
  06-completed/                 # Completed tasks
```

Task IDs are allocated sequentially by scanning every stage directory under `work/`,
so a task keeps its ID as it moves between stages. The ID prefix and zero-padded
width are defined by `task_id_prefix` / `task_id_format` in `.flow/config.toml`
(e.g. `DFT-0000` → `DFT-0001`, `DFT-0002`, ...).

## Tooling

### Turbine (dft)

Turbine is the deterministic CLI tool for this warehouse. Use `dft <command>` for:
- Warehouse scaffolding (`dft init`)
- Skill management (`dft skills add|remove|list|update|clean|search|info|create`)
- Task workflow management (`dft task create|next|claim|map`)
- Configuration checks (`dft config check`)
- Activity bindings (`dft activity start|sync|list|status|unbind`)
- Reporting (`dft reports numbers`) and sync profiles (`dft sync`)
- Telemetry controls (`dft telemetry status|flush|clear|disable`)

### Taskfile Integration

If a `Taskfile.yml` is present, use `task <command>` for common operations (test, build, lint, format). Exact canonical commands for this warehouse belong in the **Stack & Entry Points** section above.

## Boundaries

Never, without explicit instruction from the human:

- Rename, renumber, or recycle existing task IDs.
- Change `task_id_prefix` or `task_id_format` in `.flow/config.toml`.
- Move a task between `work/` stages by hand — use `dft task` commands.
- Install, update, or remove skills outside `dft skills …`, or act on skills that are not present under `skills/`.
- Delete phase artefacts under `signal/`, `explore/`, `govern/`, or `evolve/`.
- Commit secrets, tokens, credentials, or absolute local paths.

Ask first before:

- Modifying `.flow/config.toml` or the scaffold structure.
- Adding new runtime dependencies.
- Introducing a new workflow stage, skill, or phase agent.

## Commits & Branches

This project follows [Conventional Commits](https://www.conventionalcommits.org/) and [Conventional Branches](https://conventional-branch.github.io/) standards.

### Commit Format

```
<type>(scope): <description>
```

### Branch Format

```
<type>/scope-slug
```

### Change Types

| Type | Activity | Example |
|------|----------|---------|
| `plan` | Planning session | `plan(DFT-0098): Feature name` |
| `impl` | Implementation | `impl(DFT-0098): Feature name` |
| `feat` | User-visible functionality | `feat(DFT-0098): Add CSV export` |
| `fix` | Bug fix | `fix(DFT-0098): Handle empty input` |
| `refactor` | Internal restructuring | `refactor(DFT-0098): Extract service` |
| `test` | Tests only | `test(DFT-0098): Add regression cases` |
| `docs` | Documentation | `docs(DFT-0042): Update guidelines` |
| `spec` | Specification | `spec(DFT-0050): Spec name` |
| `chore` | Tooling / housekeeping | `chore: Bump dependencies` |
